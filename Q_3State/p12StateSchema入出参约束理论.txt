"""State出参入参约束"""
"""
⭐⭐⭐
实现方式：再额外定义input_schema和output_schema类
即再构建图的时候上传参数:
    builder=StateGraph(state_schema=……,       #全局状态
                    input_schema=……,          #传入限定入参的类名
                    output_schema=……)         #传入限定出参的类名

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

LangGraph提供三层 TypedDict类型约束，
用来严格区分全局完整状态、图允许外部输入字段、图对外输出字段，三者职责完全隔离
这种设计将状态的“内部运作”与“外部接口”进行了隔离，类似于后端开发中的“网关”和“内部数据库”的概念。这三层类型约束分别是：

1、state_schema(完整全局状态)★☆★一般我们用这个。图的内部完整状态空间（相当于“公共数据库”）
    图内部所有节点全程共享的完整状态字典，它包含了整个图运行过程中，所有节点可能需要读写的全部字段。图内部的任何节点都可以访问和修改这个完整状态。
    是整张图运行的完整数据容器。节点读写、状态合并全部基于这套完整结构。

2、input_schema(外部入参规范)
    限制外部调用invoke()时，只允许传入的键值对; ★外部多传多余key 会被直接过滤，不会写入全局state，实现入参校验与隔离。

3、output_schema(对外出参规范)
    限制invoke执行结束返回结果里只包含指定key; 内部大量中间、私有状态不会暴露给调用方，实现输出收口、隐私隔离。
    只有在这个 Schema 中定义的字段才会被输出，从而很好地保护了内部中间状态或敏感数据不被泄露

三者搭配实现：外部只传必要参数 → 内部自由扩展私有中间状态 → 外部函数只拿目标，私有数据全程对内不可见

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

LangGraph 设计这三层 Schema，核心目的是为了实现“内外隔离”与“数据解耦”。
如果把 LangGraph 的工作流比作一个“黑盒工厂”，这三层 Schema 就像是工厂的内部仓库、收货区和发货区。它们的具体作用和设计初衷如下：
1. 全局状态（Overall State / state_schema）
    相当于：工厂内部的“全量仓库”。
    作用：这是整个工作流内部所有节点共享的“超级内存”。工厂内部有 10 个车间（节点），它们可能需要用到 50 种不同的零件（字段）。
         这 50 种零件全都放在这个全量仓库里，内部节点可以随意读写。
    为什么需要它：保证工作流内部逻辑的完整性。内部处理往往非常复杂，需要大量的中间变量、临时状态、调试信息等。
2. 输入状态（Input Schema）
    相当于：工厂的“收货区/安检口”。
    作用：严格限制外部调用者（比如你的前端应用或 API 客户端）在启动这个工作流时，必须/只能提供什么数据。
    为什么需要它：
        接口纯净：外部用户不需要知道工厂内部有 50 种零件，他只需要提供 2 种核心原料（比如 user_query 和 user_id）即可。
        安全过滤：如果外部不小心（或恶意）传入了与内部同名的敏感字段，Input Schema 会将其拦截，防止外部直接篡改内部核心状态。
3. 输出状态（Output Schema）
    相当于：工厂的“发货区/质检口”。
    作用：严格限制工作流运行结束后，允许向外暴露什么数据。
    为什么需要它：
        隐藏内部实现：内部处理时可能产生了 intermediate_step_1、debug_logs、temp_token 等几十个中间变量。这些对外部毫无用处，甚至可能暴露系统架构。
                Output Schema 确保最终只把 final_answer 这种干净的结果交出去。
        版本控制与契约：当未来你要重构内部逻辑时，只要保证 Output Schema 不变，外部的调用方就完全不受影响。

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
假设你在做一个“AI 翻译助手”：
全局状态（内部）：可能包含 user_input, language_detected, raw_llm_response, translation, token_usage, retry_count, internal_debug_info 等 10 个字段。
输入状态（外部）：只需要 user_input 和 target_language 这 2 个字段。
输出状态（外部）：只需要 translated_text 和 token_usage 这 2 个字段。
总结：这三层设计的本质就是软件工程中的“高内聚，低耦合”。它让 LangGraph 既能处理极其复杂的内部逻辑（通过全局状态），又能对外提供一个极其简单、安全的 API 接口（通过输入/输出状态）。
"""


"""
State可以是TypedDict类型（最常用），也可以是pydantic中的BaseModel类型（即状态函数里面的继承）

对比项                TypedDict                BaseModel (Pydantic)
来源                Python标准库(typing)            Pydantic 库
定位               类型提示(轻量客典类型)         强类型数据模型(含验证逻辑)
运行时检查            无运行时校验              自动校验字段类型、默认值等☆
继承自                 dict                        BaseModel
性能                快(仅静态类型提示)            稍慢(需要解析和验证)
序列化/反序列化          手动处理                 自动.dict()，.json()
用途场景              简单数据结构定义             需要验证、解析、约束的模型
LangGraph 支持      官方推荐(State类型)         不推荐(除非你自己控制模型转换)   
"""
